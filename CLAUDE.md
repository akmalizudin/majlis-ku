## What this is

A mobile-first web platform for Malaysian events (weddings, birthdays, corporate events, parties) with two products:

1. **Digital guestbook (live gallery).** The host creates an event and gets one QR code. Guests scan it and, with no app and no account, upload photos, videos, voice messages and written wishes. Uploads appear in a live gallery and a slideshow for a TV or projector at the venue.
2. **E-invitation card with RSVP.** The host picks a template, fills in event details and shares a WhatsApp-friendly link. Guests see the details, map and countdown, and submit an RSVP.

The full product brief is `docs/brief.md`. Languages: Bahasa Melayu (default) and English. Currency MYR. Timezone `Asia/Kuala_Lumpur`.

## Process

`playbook.md` is the process: gates 0 to 7, git and branch rules, validation commands, Definition of Ready and Done, review checklist. Short version: classify, discover, set up a worktree, write the spec, write the TDD plan (the developer approves both), confirm the baseline, implement test-first, verify with fresh output, let the developer choose commit, push, or PR, then hand off. Do not commit or push without the developer's say-so.

The product is built in the eight phases listed in `docs/brief.md`. Each phase gets its own spec (`docs/specs/phase-<n>-<slug>.md`) and plan (`docs/plans/phase-<n>-<slug>.md`). After a phase: run the app, run the tests, summarise, and wait for the developer's "continue".

Worktrees: `sh scripts/worktree-add.sh <branch>` creates `.worktrees/<branch>` so agents can work in parallel; `sh scripts/worktree-cleanup.sh` removes merged ones.

## Current priorities

Decided by the developer on 2026-10-20: **get the whole system working locally first.** No hosting decision and no payment gateway yet. Plans and limits are still enforced, and an admin can set an event's plan by hand; the real `PaymentProvider` (phase 6) waits until the developer asks for it. Local development needs only Node.js: the database runs through `embedded-postgres` and media is stored on the local disk behind the same storage interface that S3 or R2 will use later.

## Stack

Do not change the stack or add a paid service without the developer's approval.

| Concern | Choice |
| --- | --- |
| Framework | Next.js (App Router), TypeScript strict, Tailwind CSS, installable PWA |
| Database | PostgreSQL with Prisma 6; locally through `embedded-postgres` (no Docker needed) |
| Auth (hosts only) | Auth.js v5: email magic link (printed to the server log in development) and Google sign-in |
| Media storage | `StorageDriver` interface: `local` (disk, signed upload and download URLs served by the app) now; S3-compatible (R2 or S3) with direct-from-browser presigned uploads later |
| Media processing | Client-side image compression; server-side thumbnails with `sharp`; capped video length and size; voice notes converted to a web-friendly format |
| Realtime | Server-Sent Events for the live gallery and slideshow |
| Payments | Deferred. Later: a Malaysian gateway (FPX, e-wallets, cards) behind a `PaymentProvider` interface, with verified webhooks |
| Validation | Zod at every boundary |
| Tests | Vitest for business logic, Playwright e2e for the guest upload flow and the payment flow (sandbox) |
| Deploy | Local first. A Dockerfile and hosting come later |

## Rules

1. **Server owns the truth.** Prices, plan limits, quotas, and moderation state are computed on the server from the database. Never trust a price, size, kind, or count sent by the client.
2. **Validate every boundary with Zod.** Route handlers, server actions, webhooks, env variables (`src/lib/env.ts`), and form input.
3. **Domain logic lives in `src/server/<domain>/`** as plain, unit-tested functions. Route handlers and server actions only parse input, check auth, call the domain function, and shape the response.
4. **Guests have no account.** A guest is a display name plus a device token in a cookie, scoped to one event. Never ask a guest for an email, phone number, or login to upload.
5. **Private by default.** Galleries are private unless the host makes them public. Media is served through short-lived signed URLs. An optional event PIN gates guest access.
6. **Uploads go straight to object storage** with presigned URLs. The server issues the URL only after checking plan limits, size, and declared type, then confirms the object (magic bytes, size) before it becomes visible.
7. **Money is integer sen** (`priceSen`, `amountSen`), currency `MYR`. Never use floats for money.
8. **Payments go through `PaymentProvider`.** Webhooks verify the signature, are idempotent, and are the only thing that marks a payment paid.
9. **Time is stored in UTC** and shown in `Asia/Kuala_Lumpur`.
10. **Bahasa Melayu is the default locale.** Every user-facing string goes through `messages/ms.json` and `messages/en.json`; no hard-coded copy.
11. **Guest page budget:** under 150 KB of JS on first load; works on low-end Android, slow 4G, and in-app browsers (WhatsApp, Instagram, Threads).
12. **Tests first, strict typing.** `strict: true`, no `any` without a comment explaining why.

## Privacy (PDPA Malaysia)

- Consent text on the guest upload screen; the upload button stays disabled until it is shown.
- The host can delete the whole event and all its media; a purge job deletes media when retention ends.
- No raw IP addresses stored; rate-limit keys use a salted hash.
- Seed and test data are invented. No real guests' names, phone numbers, or photos in the repo.

## Secrets

`.env.example` lists every variable with a comment. Never commit `.env`. Payment gateway keys, the storage secret, and the auth secret live only in `.env` or the deploy platform's secret store.
